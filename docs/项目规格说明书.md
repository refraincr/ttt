## Problem Statement

县综治中心需要将分散在职能部门、乡镇和基层单位的事件数据统一归集，识别同一人员、同一事件和风险信号，并协调部门跟进处置。各来源字段、格式和分类不一致，重复上报可能重复计数，同名或身份冲突可能导致错误归档，未经解释的风险等级也无法支持人工研判。

普通部门需要方便地上报和修正本部门数据、处理被派发的任务，同时不能因此获得跨部门档案访问权限。中心需要查看全局数据，确认不确定的匹配、解释风险、调整误判并保留完整历史。

项目交付者需要完成可独立运行、具备真实持久化的教学实习项目，覆盖课题全部 26 项功能，并提供可复现的部署、测试和演示材料。系统使用虚构或脱敏数据，风险结果仅用于教学演示。

## Solution

建设一个以县综治中心为分析研判主体、其他单位为数据上报及风险处置主体的完整前后端业务系统。通过表单、CSV、xlsx 和模拟外部系统 API 接收事件，保留原始数据，按来源映射字段并完成清洗、标准化、人员匹配和重复审核。

每条事件关联一名主要当事人。确认归属且不重复的有效事件进入人员档案，按累计次数、关键词和特殊上报来源计算低、中、高风险，并展示具体依据。身份不足或疑似重复的数据进入人工审核，不提前计入风险。

中心对风险预警进行研判，向一个承办部门派发关联具体事件的任务；部门记录跟进、提交结果，中心审核、退回或关闭。预警、任务、事件办结和人员风险分别管理。全程提供角色与部门权限、变更审核、统计导出和操作追溯。

## User Stories

1. 作为系统使用者，我希望登录和退出系统，以便在自己的授权范围内操作。
2. 作为中心管理员，我希望维护账号、部门和角色，以便配置参与单位及工作人员。
3. 作为中心管理员，我希望系统管理权限与业务研判权限分开，以便明确职责。
4. 作为中心管理员，我希望同一账号可以兼任多种角色，以便适应人员兼岗和演示需要。
5. 作为部门工作人员，我希望分别获得上报和处置权限，以便只执行被授权的业务。
6. 作为部门上报人员，我希望只查看本部门记录，以便在明确的数据边界内工作。
7. 作为中心研判人员，我希望查看跨部门数据和人员档案，以便综合研判。
8. 作为特殊上报人员，我希望使用归属部门的特殊账号上报不同当事人的事件，以便系统记录可信的特殊来源。
9. 作为中心管理员，我希望维护来源名称、类型和状态，以便识别不同接入渠道。
10. 作为中心配置人员，我希望为来源维护字段映射和类型转换，以便处理不同格式的输入。
11. 作为中心配置人员，我希望维护分类字典和来源别名，以便各部门使用一致的统计口径。
12. 作为部门上报人员，我希望通过表单录入单条事件，以便及时提交数据。
13. 作为部门上报人员，我希望在提交前修改或删除草稿，以便更正录入错误。
14. 作为部门上报人员，我希望下载统一模板并上传 CSV 或 xlsx，以便批量录入。

16. 作为导入人员，我希望系统只自动修正不改变含义的格式问题，以便避免错误猜测原意。
17. 作为导入人员，我希望无效日期、无效身份证号及未知分类给出逐行原因，以便定位错误。

20. 作为导入人员，我希望重试不重复生成已成功事件，以便避免重复计数。
21. 作为中心代导入人员，我希望选择归属部门并记录实际操作人，以便明确数据责任。
22. 作为接口调用方，我希望通过绑定来源和部门的凭据批量提交数据，以便演示外部系统接入。

## Implementation Decisions

以下业务决定已由用户确认；模块划分和三层存储结构是此前设计中提出的实现方案，不意味着已有代码。

1. **技术与界面**：采用 Vue 3、TypeScript、Element Plus、Spring Boot 和 MySQL 8.0。界面为左侧导航、列表筛选、详情及首页概览组成的实用后台。
2. **模块边界**：建设身份权限、部门来源与字典、接入与质量、匹配去重与档案、规则与风险、预警处置、统计导出及审计模块。不扩建完整信访办理系统。
3. **主表兼容**：保留 `tb_input_record` 的全部既有字段，允许增加字段和配套表。既有匹配、复核、关键词和风险字段不能代替完整的审核状态及计算证据。
4. **事件存储层次**：建议区分原始接收记录、标准化来源上报记录、统一有效事件。跨部门来源记录保留并关联同一业务事件，不以最后上报覆盖其他来源。
5. **人员关系**：一条事件只归一名主要当事人；人员档案可以归集多条有效事件，其他被提及人员不参与自动归档。
6. **分权与范围**：中心管理员和研判人员分开；部门上报与处置权限分开；允许兼任。普通部门不能查看跨部门档案、综合风险等级或其他部门原始事件。
7. **特殊账号**：由工作人员使用，必须属于部门，可上报不同人员；特殊来源来自可信账号或凭据，不能由文件赋予，不等同于部门或事件类型。
8. **输入契约**：支持表单、CSV、xlsx 和凭据认证的批量 API；API 提供外部编号、来源范围内重复保护、逐条接收结果和记录查询。具体端点及字段契约尚待实现设计，不在此虚构。
9. **映射与字典**：按来源保存列映射、明确转换及分类别名；表单选择标准字典。缺必填列提前提示，未知分类值使对应行失败。
10. **清洗边界**：只修正不改变含义的格式。必填缺失、无效日期及已填写但无效的身份证号失败；身份缺失可以入审核池，不等于允许建档。
11. **批量结果**：部分成功，逐行错误，失败文件可修正重导；重复提交不新增有效事件。来源、批次、原始行号、原始内容与操作身份可追溯。
12. **可信归属**：普通账号仅向自身部门上报；中心代导入需明确归属并记录操作者；接口凭据绑定部门、来源及特殊上报权限。
13. **自动匹配**：有效身份证号与姓名一致才自动关联；姓名冲突转人工，手机号差异不覆盖档案。新身份证号与姓名齐全且无冲突可自动建档。
14. **无身份证号处理**：姓名与有效手机号唯一且无冲突可自动匹配。未匹配的新人员必须人工确认建档并填理由。人工建档最低为身份证号与姓名，或姓名与有效手机号；身份不足不建档。
15. **审核顺序**：新提交不设全量内容审批。先清洗校验，再身份确认，再重复审核，最后参与计数；待身份审核和疑似重复不能提前计风险。
16. **去重**：同来源相同外部编号及同批完全重复不重复计数；疑似重复按同人、默认三天内和描述相似筛选，窗口及阈值可配，人工确认合并或独立。
17. **有效口径**：计数单位是身份已确认、重复已明确且未删除的独立有效事件。来源上报数与有效次数分开；办结不减少累计次数。
18. **基础风险**：累计 0～2 条低、3～4 条中、至少 5 条高；次数阈值可配置。只使用低、中、高三档，待审核另列状态。
19. **保底规则**：特殊来源固定最低中风险，不可停用或人工调低突破。初始单词参考“扬言”“杀人”“跳楼”，组合参考“婚＋欠”“婚＋钱”；关键词规则可配置启停，不降低已有高风险。
20. **组合与误命中**：组合限同一事件的问题描述或标签，不跨事件凑词。第一版字面匹配，中心可按原因排除具体误命中；相关文本或对应规则变化使排除失效。
21. **结果解释**：分别展示规则等级、有效人工调整和最终等级，保存次数、命中规则、文本、事件、来源及计算依据。特殊来源在业务合并中不得丢失。
22. **人工等级**：调整必填原因；影响风险的数据或规则变化使调整失效并重算，无关联系方式修改不因此失效；若引起重新归档则按影响风险处理。
23. **规则生命周期**：草稿、影响预览、发布及版本留存。发布前展示预计升降级数量，发布后重算受影响档案，同步人工调整有效性和预警。
24. **数据变化**：新增、修改、删除、重新归档、合并、拆分后更新相关统计与风险；事件迁移同时重算原、新人员。事件和任务办结不直接降级。
25. **修改审批**：草稿可自行修改删除；已归档记录修正或删除由部门申请、中心批准后生效，待审沿用旧版本，保存前后历史。
26. **风险预警**：首次进入中高风险、等级上升时提示；已有开放风险预警则更新并标记新增信息；处置超期单独提示。关闭后新有效事件或等级上升可再次触发。
27. **时限**：默认七天未完成预警研判提醒，可配置。任务按截止时间判断部门超期；结果已提交进入中心待审后单独展示等待时长。
28. **任务契约**：每项任务关联一个人员、至少一条有效事件、一个承办部门和期限；同人可多任务。派发保留信息快照，向部门只开放中心明确提供的必要信息。
29. **处置状态**：部门跟进、提交，中心审核通过关闭或退回补充；中心明确选择需要办结的关联事件，不默认全部办结。
30. **预警关闭**：中心填写结论后明确关闭，可研判暂不派发；任务完成与预警关闭分别管理，关闭不更改风险等级。
31. **归档变化影响**：已关闭任务快照保留；未完成任务标记归档变化、暂停提交办结，中心确认人员、事件及部门后继续。
32. **统计导出**：支持风险等级、姓名、关键词、来源、部门、时间筛选；统计风险分布、类型、部门上报量、热点词和待审数；导出与详情、附件均遵守相同授权范围。
33. **审计与一致性**：关键操作记录主体、时间、对象、原因及前后变化。事务、版本检查和幂等任务是设计建议，用于防止并发审核重复生效、旧重算覆盖新结果及预警重复生成。
34. **规模与运行**：以约十万事件、一万档案、单批一万行和约二十人同时使用为目标；导入与批量重算提供后台进度。提供本机开发启动与 Docker Compose 部署。

## Testing Decisions

1. **已知基础**：当前没有应用代码、测试框架或既有测试入口，也没有可复用的代码测试先例。已有的 26 项功能映射和 63 项待执行检查是验收基础，不是测试通过证据。
2. **主要入口建议，尚未单独确认**：优先以公开业务 API 加真实 MySQL 集成测试覆盖接入、审核、归档、风险与处置。由外部请求驱动，再通过可观察的查询结果、权限响应、导出和审计验证行为，避免为每个内部类建立新的测试入口。本建议是本次综合提出，不冒充此前用户已作出的测试架构决定。
3. **测试原则**：断言用户可见行为、业务约束、持久化结果和错误反馈，不断言内部函数调用次数、私有方法、表数量或具体实现算法。规则边界需要时使用少量参数化行为测试，避免机械复刻实现。
4. **接入模块**：覆盖两种以上来源、CSV 与 xlsx 映射、必填缺列、未知字典、格式修正、无效身份证、部分成功、失败文件、API 凭据和幂等重试。
5. **人员模块**：覆盖身份证姓名一致与冲突、手机号差异、自动建档、姓名手机号唯一匹配、人工建档理由以及身份不足始终待审。
6. **重复模块**：覆盖同来源编号、同批完全重复、三天窗口边界、疑似暂不计数、先身份后重复、跨部门合并只计一次与来源权限不变。
7. **风险模块**：覆盖 0、2、3、4、5 条边界，单词、同事件组合及跨事件不组合，特殊保底不被突破，误命中排除及失效，人工调整及失效，办结不降级和删除后重算。
8. **变更与规则模块**：覆盖申请待审旧版本有效，审核后重算，档案合并拆分双向统计，草稿不影响当前结果，发布影响预览和新版本重算，旧计算不能覆盖新结果。
9. **预警处置模块**：覆盖开放预警更新、关闭后重新触发、七天未研判、任务截止、结果待审责任切换、授权信息、退回补充、明确事件办结，以及归档变化暂停任务。
10. **权限及审计**：除页面入口控制外，通过不同身份请求详情、列表、导出及附件验证服务端范围；验证管理员未兼任无研判权限、部门不越权、特殊来源不可伪造和关键原因留存。
11. **前端验证建议**：少量浏览器端完整链路测试验证页面与真实后端连通，重点走导入失败修正、人工审核、风险解释、任务反馈及中心关闭，不以 Mock 页面代替后端验收。
12. **时间与批量验证建议**：在业务边界控制测试时间，覆盖未研判及任务期限，不依赖长时间真实等待；用可重复虚构数据验证十万事件、一万档案、单批一万及约二十并发，记录环境、操作组合、结果一致性与实际性能。
13. **交付验证**：在独立环境按本机说明及 Compose 配置启动，验证初始化、样例账号、API 示例和完整业务演示。性能数字目前是目标，响应时间和吞吐未约定，不编造已达成指标。

## Out of Scope

- 完整信访审批、流转、回访和评分系统。
- 一条事件关联多名参与风险计算的当事人。
- 普通部门自由查看跨部门人员完整档案。
- 一项任务的多部门主办、协办流程。
- 所有事件进入匹配前先做人工内容审批。
- 缺少可靠身份时仅凭姓名创建待补全档案。
- 跨来源疑似重复自动合并或审核前先计风险。
- 跨事件拼凑组合关键词。
- 将待人工审核设为第四档风险，将特殊账号当作部门或事件类型。
- 通过办结自动减少累计风险次数、自动降级，或自动关闭风险预警。
- 允许人工等级突破特殊来源最低中风险约束。
- `.xls`、含宏文件、图片识别导入。
- 第一版语义理解、机器学习、自然语言分类、关系图、地图和独立展示大屏。
- 真实政务系统对接、真实群众敏感数据及生产级部署标准。
- 本次生成应用代码、建库迁移执行、部署或发布未经配置的远程 issue。
