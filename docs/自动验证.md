# 自动验证

从项目根目录执行：

```sh
node scripts/verify.mjs
```

需要 Node.js 22、Java 21 或以上、Maven、可用的 Docker Engine 和 Compose，以及首次安装依赖和镜像所需的网络。Linux 安装浏览器系统依赖时可能需要 sudo。Windows 与 Linux 使用同一入口。运行前停止该工作副本中的 Vite 开发服务：入口会执行 `npm ci`，Windows 上运行中的服务会锁定原生依赖文件。

脚本先检查 Docker 可用性，再依次运行后端 `mvn -B verify`、前端依赖安装、类型检查、生产构建，以及真实 MySQL 上的 HTTP 和浏览器测试。后端 Maven 同时运行可控时钟测试；完整业务行为由真实 MySQL API 和浏览器测试验证。每个阶段分别报告结果；前置阶段失败后，后续阶段不执行，整体返回非零退出码。

业务验证使用独立的 `compose.verify.yml`，每次生成随机 Compose 项目名、全新数据库卷及随机本机网页端口，不连接已有演示数据库。数据库和 API 不发布宿主机端口。验证使用固定的虚构演示密码，仅用于临时环境；不会加载本机 `.env`。测试结束或正常中断后收集日志并删除本次容器和数据卷。强制结束进程或机器断电会跳过清理，可按日志中的项目名手动清理：

```sh
docker compose --env-file .env.example -f compose.verify.yml -p <本次项目名> down --volumes --remove-orphans
```

日志和分阶段结果位于 `.local/verification/<项目名>/`；浏览器报告位于 `frontend/playwright-report/`，失败 trace 位于 `frontend/test-results/`。报告可能包含测试中的来源正文，应按测试数据处理。

只执行隔离业务验证（仍安装前端与浏览器依赖，并构建应用镜像）：

```sh
node scripts/verify.mjs --behavior-only
```

只验收容器启动与重建后的持久化（不要求宿主机 Java/Maven，不安装浏览器，但仍执行 `npm ci`）：

```sh
node scripts/verify.mjs --startup-only
```

三种模式均会构建并启动全新的 MySQL/API/web 容器，通过 Nginx 检查生产页面及其 JS/CSS 资源、匿名 API 拒绝访问、管理员登录和配置写入。随后先保存服务日志，执行不带 `--volumes` 的 `down` 再 `up`，重新获取随机网页端口，等待应用就绪并重新登录，核对先前写入的字典记录所有字段一致。这同时覆盖 MySQL 迁移、初始化、容器间代理和命名卷保留。最终清理才删除本次临时数据卷。全量与业务模式在此之后继续运行原有业务测试，CI 的业务 job 同样执行这些启动验收。

GitHub Actions 的 `Verification` 工作流在 push、pull request 和手动触发时运行。后端编译打包、前端类型与构建、业务验证为三个独立 job；业务 job 自动上传日志、HTML 报告及失败 trace。仓库管理员可将这三个检查设为分支保护的必需检查。

现有 `frontend/npm test` 仍用于已启动的手动验证环境；它会写入数据，不能用于业务数据库。自动入口始终使用新库，避免既有数据影响依赖初始样例的断言。
